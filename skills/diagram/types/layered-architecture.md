# 分层架构图 layered-architecture

回答：**系统由什么组成、分几层、本次改动落在哪里。** 不表示先后顺序。

样式：横向色带，从上到下是层，左侧是层名，层内是模块卡片。新增模块绿框，修改模块橙框。

## 数据格式

```json
{
  "type": "layered-architecture",
  "title": "规则引擎由什么组成",
  "summary": "新增规则层三个模块，执行层两个适配器需要修改",
  "layers": [
    {
      "name": "交互层",
      "modules": [
        { "name": "工作台界面" },
        { "name": "命令行", "code": "cli/" }
      ]
    },
    {
      "name": "规则层",
      "modules": [
        { "name": "规则引擎", "code": "engine/", "status": "new", "note": "确定性状态机" }
      ]
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `layers` | 从上到下排列，建议 3～5 层，每层 1～4 个模块 |
| `modules[].name` | 必填，≤ 12 字 |
| `modules[].code` | 可选，对应的代码路径或服务名 |
| `modules[].status` | 可选：`new` 新增 / `changed` 修改 / `risk` 有风险；不填表示不变 |
| `modules[].note` | 可选，一行小字补充 |

## 规则

- 层的划分按职责（交互、编排、领域、执行、存储等），同一层的模块在同一抽象级别。
- 模块总数 ≤ 12。某一层模块太多时，把它单独下钻成一张图。
- 只画组成，不画箭头；依赖关系明显由上下层表达。确实需要强调某条跨层依赖时，写在 `summary` 里。
