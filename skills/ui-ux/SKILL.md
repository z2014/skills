# UI/UX 设计与交互打磨

把参考界面的视觉规律转成项目可复用的设计规则，再把交互补全到可操作、可中断、可恢复。沿用项目的技术栈、组件库和品牌，不预设某种产品风格。

## 1. 确定目标与依据

- 识别用户要做的是参考还原、视觉统一，还是交互改进。只修改相关页面和状态。
- 阅读已有主题变量、基础组件和相邻页面。先找可复用的规则，再决定是否补充。
- 有参考界面时，记录参考来源、视口或容器尺寸、主题和交互状态。区分源码实测、界面观察和估计值。
- 只有截图时，不推断截图未展示的动效、焦点顺序或错误处理。根据项目惯例补齐，并说明假设。
- 没有参考界面时，以项目现有规范为起点。只有会改变设计方向的信息缺失时，才向用户澄清。

## 2. 建立视觉契约

涉及视觉提取或样式统一时，读取 [设计系统提取](references/design-system.md)。

先在工作上下文中建立一份精简映射：**观察到的规律 → 语义用途 → 项目已有变量或组件 → 必要补充**。不要求为每次修改新建文档。

- 按表面、文本、边框、强调色、排版、间距和圆角归纳规则。
- 同时定义适用的默认、悬停、按下、焦点、禁用和加载状态。
- 优先补齐已有变量或组件的状态，不为相同用途创建另一套主题或控件。
- 品牌色、低对比表面、边框层数和弹簧参数属于具体设计选择。只有参考或项目要求时才采用。

## 3. 定义交互契约

涉及动效、拖拽、分栏、滚动或键盘操作时，读取 [交互打磨](references/interactions.md)。

对本次修改的交互，明确：**触发条件 → 进行中反馈 → 完成结果 → 取消或失败后的状态**。

- 先保证操作结果正确，再选择表达反馈的动效。
- 拖拽和自动滚动必须让用户能够接管。中断后恢复可操作状态。
- 为鼠标以外的操作提供等价入口。收起文字、折叠面板或改变布局后，保留可访问名称和恢复入口。
- 动效关闭或被快速打断时，业务结果、焦点和最终布局仍然正确。

## 4. 实现最小完整改动

- 先完成一个代表性组件及其必要状态，再把确认过的规则用于同类界面。
- 优先使用项目已有的组件、CSS 能力和动效设施。只有现有能力无法满足需求时，才考虑新增依赖。
- 把重复的视觉值放入已有主题系统。只提取本次确实重复的结构或行为。
- 参考源码的注释与实现不一致时，检查实际事件路径。不要把示例中的缺失行为一起复制。

## 5. 按场景验证

仅检查本次涉及的场景，使用项目已有的检查和测试入口。

| 场景 | 验证结果 |
| --- | --- |
| 视觉还原或统一 | 在相同视口、主题和状态下比较，先修正结构、排版和间距，再调整装饰 |
| 多状态组件 | 加载、空数据、错误、禁用等适用状态保持可读，关键操作仍可发现 |
| 窄容器与内容变化 | 长文本、实际业务语言和数字变化不会挤掉主操作或造成非预期溢出 |
| 键盘操作 | 焦点可见，操作顺序正确，关闭浮层后焦点回到合理位置 |
| 动效与连续操作 | 快速重复操作、打断动画和减少动态效果模式不影响结果 |
| 拖拽与分栏 | 越界、中断、折叠和恢复后不残留拖拽状态或遮罩 |

修复非平凡的交互逻辑时，为关键行为增加回归检查。浏览器交互不能只用类型检查代替。

交付时简述采用的视觉规则、改动后的行为、实际验证结果和剩余限制。无法运行界面时，明确标注未验证项，不宣称视觉或交互已验收。
