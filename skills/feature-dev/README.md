# 功能开发插件（Feature Development Plugin）

一套全面、结构化的功能开发工作流，配有专门的 agent，分别负责代码库探索、架构设计和质量审查。

## 概述

功能开发插件提供系统化的 7 阶段方法来构建新功能。它不会直接跳到写代码，而是引导你理解代码库、提出澄清问题、设计架构、保证质量，最终得到设计更好、与现有代码无缝集成的功能。

## 理念

构建功能不只是写代码。你需要：
- 在修改之前**理解代码库**
- 通过**提问**澄清模糊的需求
- 在实现之前**认真设计**
- 在构建之后**审查质量**

本插件把这些实践嵌入一个结构化的工作流，使用 `/feature-dev` 命令时会自动执行。

## 命令：`/feature-dev`

启动一个引导式的功能开发工作流，包含 7 个不同的阶段。

**用法：**
```bash
/feature-dev 添加基于 OAuth 的用户认证
```

或者直接：
```bash
/feature-dev
```

该命令会以交互方式引导你完成整个流程。

## 7 阶段工作流

### 阶段 1：需求理解（Discovery）

**目标**：弄清楚要构建什么

**会发生什么：**
- 如果功能需求不清楚，进行澄清
- 询问你要解决什么问题
- 识别约束和要求
- 总结理解并与你确认

**示例：**
```
你：/feature-dev 添加缓存
Claude：我先了解一下你的需求……
        - 要缓存什么？（API 响应、计算结果等）
        - 你的性能要求是什么？
        - 有偏好的缓存方案吗？
```

### 阶段 2：代码库探索（Codebase Exploration）

**目标**：理解相关的现有代码和模式

**会发生什么：**
- 并行启动 2-3 个 `code-explorer` agent
- 每个 agent 探索不同的方面（相似功能、架构、UI 模式）
- agent 返回全面的分析，并附上需要阅读的关键文件
- Claude 阅读所有找出的文件，建立深入理解
- 全面总结发现的内容

**启动的 agent：**
- "找出与 [功能] 相似的功能并追踪其实现"
- "梳理 [领域] 的架构和抽象"
- "分析 [相关功能] 的当前实现"

**示例输出：**
```
找到的相似功能：
- 用户认证（src/auth/）：使用 JWT token，中间件模式
- 会话管理（src/session/）：基于 Redis，24 小时过期
- API 安全（src/api/middleware/）：限流、CORS

需要理解的关键文件：
- src/auth/AuthService.ts:45 - 核心认证逻辑
- src/middleware/authMiddleware.ts:12 - 请求认证
- src/config/security.ts:8 - 安全配置
```

### 阶段 3：澄清问题（Clarifying Questions）

**目标**：补齐信息缺口，消除所有模糊点

**会发生什么：**
- 回顾代码库探索结果和功能需求
- 找出未明确的方面：
  - 边界情况
  - 错误处理
  - 集成点
  - 向后兼容
  - 性能要求
- 以有条理的列表提出所有问题
- **等你回答后再继续**

**示例：**
```
在设计架构之前，我需要确认：

1. OAuth 提供方：用哪些 OAuth 提供方？（Google、GitHub，还是自定义？）
2. 用户数据：存储 OAuth token，还是只存用户资料？
3. 现有认证：替换现有认证，还是与之并存？
4. 会话：是否与现有的会话管理集成？
5. 错误处理：OAuth 失败时如何处理？
```

**关键**：这个阶段确保设计开始前没有任何模糊之处。

### 阶段 4：架构设计（Architecture Design）

**目标**：设计多种实现方案

**会发生什么：**
- 启动 2-3 个侧重不同的 `code-architect` agent：
  - **最小改动**：改动最小，复用最多
  - **整洁架构**：可维护性，优雅的抽象
  - **务实平衡**：速度与质量兼顾
- 审阅所有方案
- 判断哪个最适合当前任务
- 呈现方案对比，包括取舍和推荐
- **询问你倾向哪个方案**

**示例输出：**
```
我设计了 3 个方案：

方案 1：最小改动
- 在现有 AuthService 中扩展 OAuth 方法
- 在现有 auth 路由中添加新的 OAuth 路由
- 只需少量重构
优点：快，风险低
缺点：OAuth 与现有认证耦合，更难测试

方案 2：整洁架构
- 新建 OAuthService，使用独立的接口
- 独立的 OAuth 路由和中间件
- 重构 AuthService，使用公共接口
优点：职责分离清晰，可测试，可维护
缺点：文件更多，重构更多

方案 3：务实平衡
- 新建 OAuthProvider 抽象
- 集成到现有 AuthService 中
- 少量重构，边界清晰
优点：复杂度与整洁度平衡
缺点：仍有一些耦合

推荐：方案 3。它在不过度重构的前提下提供清晰的边界，
也很契合你现有的架构。

你想用哪个方案？
```

### 阶段 5：实现（Implementation）

**目标**：构建功能

**会发生什么：**
- 开始前**等待你的明确批准**
- 阅读前面阶段找出的所有相关文件
- 按选定的架构实现
- 严格遵循代码库约定
- 编写整洁、文档完善的代码
- 随进展更新待办

**说明：**
- 只有在你批准后才开始实现
- 遵循阶段 2 发现的模式
- 使用阶段 4 设计的架构
- 持续跟踪进度

### 阶段 6：质量审查（Quality Review）

**目标**：确保代码简洁、DRY、优雅且功能正确

**会发生什么：**
- 并行启动 3 个侧重不同的 `code-reviewer` agent：
  - **简洁/DRY/优雅**：代码质量和可维护性
  - **Bug/正确性**：功能正确性和逻辑错误
  - **约定/抽象**：项目标准和模式
- 汇总发现
- 找出最高严重级别的问题
- **呈现发现并询问你想怎么处理**：
  - 现在修复
  - 稍后修复
  - 保持现状继续
- 根据你的决定处理问题

**示例输出：**
```
代码审查结果：

高优先级问题：
1. OAuth 回调中缺少错误处理（src/auth/oauth.ts:67）
2. 内存泄漏：OAuth state 未清理（src/auth/oauth.ts:89）

中优先级：
1. token 刷新逻辑可以简化（src/auth/oauth.ts:120）
2. 考虑把 OAuth 配置校验提取出来

所有测试通过。代码遵循项目约定。

你想怎么处理？
```

### 阶段 7：总结（Summary）

**目标**：记录完成了什么

**会发生什么：**
- 将所有待办标记为完成
- 总结：
  - 构建了什么
  - 做出的关键决策
  - 修改的文件
  - 建议的后续步骤

**示例：**
```
功能完成：OAuth 认证

构建的内容：
- 支持 Google 和 GitHub 的 OAuth 提供方抽象
- 与现有认证集成的 OAuth 路由和中间件
- token 刷新和会话集成
- 覆盖所有 OAuth 流程的错误处理

关键决策：
- 采用务实方案，使用 OAuthProvider 抽象
- 与现有会话管理集成
- 添加 OAuth state 以防止 CSRF

修改的文件：
- src/auth/OAuthProvider.ts（新增）
- src/auth/AuthService.ts
- src/routes/auth.ts
- src/middleware/authMiddleware.ts

建议的后续步骤：
- 为 OAuth 流程添加测试
- 添加更多 OAuth 提供方（Microsoft、Apple）
- 更新文档
```

## Agent

### `code-explorer`

**用途**：通过追踪执行路径，深入分析代码库中的现有功能

**关注领域：**
- 入口和调用链
- 数据流和数据转换
- 架构层次和模式
- 依赖和集成
- 实现细节

**何时触发：**
- 在阶段 2 自动触发
- 探索代码时可手动调用

**输出：**
- 入口，附 file:line 引用
- 逐步的执行流程
- 关键组件及职责
- 架构洞察
- 必读文件列表

### `code-architect`

**用途**：设计功能架构和实现蓝图

**关注领域：**
- 代码库模式分析
- 架构决策
- 组件设计
- 实现路线图
- 数据流和构建顺序

**何时触发：**
- 在阶段 4 自动触发
- 需要架构设计时可手动调用

**输出：**
- 发现的模式和约定
- 架构决策及理由
- 完整的组件设计
- 列出具体文件的实现地图
- 分阶段的构建顺序

### `code-reviewer`

**用途**：审查代码中的 bug、质量问题和项目约定遵循情况

**关注领域：**
- 项目规范遵循（CLAUDE.md）
- Bug 检测
- 代码质量问题
- 基于置信度的过滤（只报告置信度 ≥80 的问题）

**何时触发：**
- 在阶段 6 自动触发
- 写完代码后可手动调用

**输出：**
- 严重问题（置信度 75-100）
- 重要问题（置信度 50-74）
- 附 file:line 引用的具体修复建议
- 项目规范引用

## 使用方式

### 完整工作流（推荐用于新功能）：
```bash
/feature-dev 为 API 端点添加限流
```

让工作流引导你走完全部 7 个阶段。

### 手动调用 agent：

**探索功能：**
```
"启动 code-explorer，追踪认证是如何工作的"
```

**设计架构：**
```
"启动 code-architect，设计缓存层"
```

**审查代码：**
```
"启动 code-reviewer，检查我最近的改动"
```

## 最佳实践

1. **复杂功能使用完整工作流**：7 个阶段确保规划周全
2. **认真回答澄清问题**：阶段 3 能避免后续的混乱
3. **慎重选择架构**：阶段 4 提供多个选项是有原因的
4. **不要跳过代码审查**：阶段 6 能在问题进入生产前发现它们
5. **阅读建议的文件**：阶段 2 找出关键文件，阅读它们以理解上下文

## 何时使用本插件

**适用于：**
- 涉及多个文件的新功能
- 需要架构决策的功能
- 与现有代码的复杂集成
- 需求不够明确的功能

**不适用于：**
- 单行 bug 修复
- 琐碎改动
- 定义明确的简单任务
- 紧急热修复

## 前提条件

- 已安装 Claude Code
- Git 仓库（用于代码审查）
- 已有代码库的项目（工作流假定有现成代码可供学习）

## 故障排查

### Agent 耗时太长

**问题**：代码探索或架构 agent 很慢

**解决方法**：
- 对大型代码库来说这是正常的
- agent 会尽可能并行运行
- 充分的探索会换来更好的理解

### 澄清问题太多

**问题**：阶段 3 提出的问题太多

**解决方法**：
- 初始功能需求写得更具体
- 预先提供约束相关的背景
- 如果确实没有偏好，就说"你觉得怎样最好就怎样"

### 架构选项让人无从选择

**问题**：阶段 4 的架构选项太多

**解决方法**：
- 相信推荐，它基于代码库分析
- 如果仍不确定，请求更多解释
- 拿不准时选择务实方案

## 提示

- **功能需求写具体**：细节越多，澄清问题越少
- **相信流程**：每个阶段都建立在前一阶段之上
- **审阅 agent 的输出**：agent 会提供关于你代码库的有价值的洞察
- **不要跳过阶段**：每个阶段都有其作用
- **用于学习**：探索阶段能帮你了解自己的代码库
